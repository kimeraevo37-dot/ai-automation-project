# Lessons Learned

## 1. Version 0.1で確認できたこと

### 確認済み事実

- 基盤3文書を作成できた。
- README.mdだけを個別タスクとして作成できた。
- 基盤3文書とREADME.mdを2段階のCommitに分けられた。
- 空フォルダがGitで追跡されない挙動を説明できた。
- 問題発見後にテンプレートを修正し、新しいリポジトリで再テストできた。
- 人間の承認を残す運用が成立した。

## 2. 初心者が迷いやすいこと

- リポジトリ名とローカルパス
- CommitとPushの違い
- Changesに表示される対象
- 空フォルダの扱い
- SummaryとCommit内容の一致
- GitHub Desktopとブラウザ版GitHubの違い
- Codexが見ている状態と人間が見ている状態の差

## 3. AIだけでは作れなかった価値

### 確認済み事実

- 実際に4ファイルがChangesへ表示された。
- 空フォルダがGitHubに表示されなかった。
- リポジトリの確認対象が一致しないと、Codexと人間の認識が食い違った。
- 修正後の二段階Commitで、README.mdだけを変更対象として確認できた。

### 教材へ転用する意味

実際に間違えた箇所、画面上のChanges、作業を止めた理由、修正を選んだ理由、再テストで解消した事実は、一般的なAI説明だけでは代替しにくい一次体験である。

## 4. 教材へ反映すべき内容

- GitHub Desktopの実画面
- 正しいリポジトリとローカルパスの確認方法
- Changesの読み方
- Commit前チェック
- Push後の確認
- 誤ったCommitをPushした場合に、慌てて履歴を書き換えない考え方
- 空フォルダの説明
- Codexが停止した場合の確認方法
- 初心者向け用語集
- トラブルシューティング

## 5. 今後検証が必要なこと

### 推測・仮説

- 第三者が同じ手順を再現できるか。
- 説明なしでもテンプレートを使用できるか。
- 実画面がどこまで必要か。
- 教材の適切な分量。
- 購入者が価値を感じる部分。
- 適正価格、更新頻度、サポート範囲。

### 未確認

- 第三者テストの結果。
- 購入者データと販売実績。
- 有料商品の適正価格。

## 6. 次バージョンへ持ち越す課題

| 優先度 | 課題 | 理由 | 完了条件 | 推奨作業時間 |
| --- | --- | --- | --- | --- |
| 高 | 教材目次の候補整理 | 一次体験を教材構成へ変換するため | 各章の目的と完了条件がある | 60分 |
| 高 | 実画面候補の一覧化 | 初心者が操作を確認できるようにするため | 画面名・撮影目的・伏せる情報を記録 | 30分 |
| 高 | Commit前チェックの具体化 | 誤った対象のCommitを防ぐため | Summary・対象・差分の確認手順がある | 30分 |
| 高 | 正しいリポジトリ確認手順 | リポジトリ取り違えを防ぐため | 名前・パス・URL・ブランチの確認項目がある | 30分 |
| 中 | 用語集候補の整理 | Git用語で止まる可能性があるため | 初心者向け候補語を一覧化 | 30分 |
| 中 | FAQ候補の整理 | 同じ不安への回答を再利用するため | 質問と確認手順を記録 | 30分 |
| 中 | 第三者テスト計画 | 再現性を確認するため | 対象者・手順・記録方法を定義 | 60分 |
| 中 | 市場調査の追加 | 価格・購入者価値の根拠が不足するため | 調査対象と確認日を記録 | 30分 |
| 低 | CHANGELOG運用の詳細化 | 更新内容を購入者へ伝えるため | 版・日付・変更理由の形式を決める | 15分 |

## 7. 記録上の区分

- **確認済み事実:** Version 0.1の通しテスト・再テスト、ファイル、Commit履歴で確認した内容。
- **推測・仮説:** 第三者や購入者がどの説明に価値を感じるか。
- **未確認:** 販売可能性、価格、第三者による再現性。
