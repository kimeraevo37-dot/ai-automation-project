# 購入者向け付録構成計画 — Version 1.0候補

## 1. 目的

教材本文を最初から読み直さなくても、購入者が用語、不安、操作ミス、想定外の状態に応じて安全な確認場所へ戻れるようにする。

この文書は、付録の役割と作成範囲を決める計画である。用語集、FAQ、Commit前チェックリスト、トラブル集の本文はまだ作成しない。第三者テストの結果は未確認であり、実際に質問された内容として扱わない。

## 2. 付録全体構成

| 付録 | 役割 | 対象場面 | Version 1.0での重要度 |
| --- | --- | --- | --- |
| 用語集 | 本文を止めずに基本用語を一文で確認する。 | Repository、Commit、Pushなどの意味で止まったとき。 | 高 |
| FAQ | 短い疑問に対し、確認先と安全な次の行動を示す。 | 省略表示、Changes、Push origin、空フォルダなどの疑問。 | 高 |
| Commit前チェックリスト | Commit直前の不安を30〜60秒で確認する。 | Summary入力後、Commitボタンを押す前。 | 最優先 |
| トラブル集 | 正常フローから外れたときに、止まる理由と安全な確認順を示す。 | 想定外のChanges、別リポジトリ、Push後のミスなど。 | 最優先 |

4付録は本文の代わりではない。本文は正常フローを順番に進める場所、付録は迷ったときの戻り場所として役割を分ける。

## 3. 用語集構成

### 説明方針

- 1用語につき、最初に一文で意味を説明する。
- 必要な場合だけ「この教材ではいつ確認するか」を一文追加する。
- 他の用語を使わないと説明できない場合は、先に基本語へ案内する。
- Gitの内部仕様や高度なコマンドは初稿の対象外とする。

### 掲載候補用語

| 用語 | 一文説明の方向 | 初稿の優先度 |
| --- | --- | --- |
| Repository | プロジェクトのファイルと変更履歴をまとめる場所。 | 必須 |
| Current repository | GitHub Desktopで現在開いているリポジトリ。 | 必須 |
| Branch | 変更履歴を分けて管理する単位。この教材では通常`main`を確認する。 | 必須 |
| main | この教材で確認する基本のブランチ名。 | 必須 |
| Changes | まだCommitしていない変更の一覧。 | 必須 |
| Diff | 変更前後の違いを確認する表示。 | 必須 |
| Summary | Commitの目的を短く書く入力欄。 | 必須 |
| Commit | 確認した変更をパソコン側の履歴へ記録する操作。 | 必須 |
| Push | Commitした履歴をGitHubへ送る操作。 | 必須 |
| Fetch origin | GitHub側の新しい情報があるか確認する操作。今回の基本手順ではPushの代わりではない。 | 後回し |
| History | Commitの履歴を見る画面または記録。 | 必須 |
| README.md | プロジェクトの目的、再開方法、安全ルールを書く案内ファイル。 | 必須 |
| AGENTS.md | Codexが作業開始時に読むプロジェクト固有のルール。 | 必須 |
| ROADMAP.md | 目的、優先順位、現在のフェーズを確認する文書。 | 必須 |
| COMPANY_RULE.md | 人間とCodexの役割、承認、停止条件を定める文書。 | 必須 |
| Private repository | 公開範囲を限定したリポジトリ。テストでは本番と分けて使用する。 | 必須 |
| Raw画像 | 加工前の記録用画像。教材掲載用には使わない。 | 後回し |
| Public画像 | 個人情報などを確認・処理した教材掲載用画像。 | 後回し |

### 本文との重複回避方針

- 本文では、その章で必要な用語だけを短く説明する。
- 用語集では、操作手順を繰り返さず「意味」と「参照するChapter」を示す。
- CommitとPushの操作順はChapter 8・10に残し、用語集では定義だけを扱う。

### 初稿で必須の用語

`Repository`、`Current repository`、`main`、`Changes`、`Diff`、`Summary`、`Commit`、`Push`、`History`、`README.md`、`AGENTS.md`、`ROADMAP.md`、`COMPANY_RULE.md`、`Private repository`

### 後回し候補

`Fetch origin`、`Raw画像`、`Public画像`、高度なBranch運用、Revert、Reset、Force push。

## 5. Commit前チェックリスト構成

### 役割

Commitボタンを押す直前に、正常フローから外れていないかを短時間で確認する。詳細な手順やトラブル対応は本文・トラブル集へ案内する。

### 項目数の目安

**7項目以内**を目安にし、30〜60秒で確認できる長さを優先する。

### 初稿に含める確認項目

1. Current repositoryは対象のテスト用または作業用リポジトリか。
2. Current branchは`main`か。
3. Changesは今回のCommit対象だけか。
4. SummaryはChangesの内容と一致しているか。
5. 個人情報・認証情報・意図しないファイルがないか。
6. 今回のCommit目的を一文で説明できるか。
7. Commit後にPushしてよい内容か。迷う場合はCommit・Pushを止める。

第1Commitと第2Commitのファイル名の違いは、本文とFIRST_TASK_PROMPTへ残す。チェックリストでは「今回のCommit対象だけか」を確認する。

## 6. トラブル集構成

各トラブルは、次の5項目で統一する。

1. 症状
2. なぜ止まるべきか
3. まず確認すること
4. 安全な戻り方
5. やらないこと

### 実体験由来の候補

| 候補 | 確認済みの事実 | 初稿での扱い |
| --- | --- | --- |
| 基盤3文書とREADME.mdが同じChangesに混在した | 基盤3文書が未CommitのままREADME.mdを作ると4ファイルが表示された。 | 必須 |
| 空フォルダがGitHubに表示されなかった | Gitは通常、空フォルダだけを追跡しない。 | 必須 |
| `.gitkeep`の扱いで迷った | 初期構成では必須にしない方針を採用した。 | 必須 |
| 別リポジトリを開いていた | GitHub DesktopとCodexが異なるローカル状態を確認した。 | 必須 |
| CodexとGitHub Desktopの状態認識が一致しなかった | 同じリポジトリ・パス・Git状態の確認が必要になった。 | 必須 |
| Summaryが重複したCommit履歴ができた | 正常フロー用には使わず、新しいPrivateテスト用リポジトリで正常例を再現した。 | 必須 |
| Push後にCommitメッセージのミスへ気づいた | Push後に慌てて履歴を書き換えない方針を採用した。 | 必須 |
| 画像撮影時に正常例と失敗例が混在した | 旧S-010は失敗例、v3由来のPublic画像を正常例と分離した。 | 後回し |

### 仮説段階の候補

| 候補 | 現在の状態 | 扱い |
| --- | --- | --- |
| Push originが表示されない | UIや接続状態の原因は未検証。 | 第三者テスト後に判断 |
| 教材と現在のUIが大きく違う | 将来起こり得るが、具体的な差異は未確認。 | 第三者テスト後に判断 |
| テスターが操作対象を見失う | 購入者・第三者の実測がない。 | 第三者テスト後に判断 |

安全な戻り方では、force push、`reset --hard`、公開済み履歴の書き換えを初心者向けの標準解決策にしない。個人情報・認証情報が含まれる場合は、操作を止めて状況を個別に確認する。

## 7. 本文との役割分担

| 場所 | 置く内容 |
| --- | --- |
| 本文 | 正常フローの手順、操作順、画像、完了条件、人間とCodexの役割。 |
| 用語集 | 用語の一文定義と参照するChapter。 |
| FAQ | 一問一答で回答できる短い疑問と、確認先。 |
| Commit前チェックリスト | Commit直前の7項目以内の安全確認。 |
| トラブル集 | 正常フローから外れた場合の停止、確認、戻り方、避ける操作。 |

本文では「なぜ今この操作をするか」を説明し、付録では「迷ったときにどこへ戻るか」を説明する。同じ手順を全文コピーしない。

## 8. 第三者テスト後に更新する箇所

| テストで確認する事実 | 反映先 | 反映方針 |
| --- | --- | --- |
| 実際に質問された内容 | FAQ | 同じ質問が繰り返される、または短い回答で解決できる場合に追加する。 |
| 実際に止まった場所 | 本文またはトラブル集 | 正常フロー内の説明不足は本文、想定外の状態はトラブル集へ分ける。 |
| 読み違え | 用語集または本文 | 用語の意味なら用語集、手順の順序なら本文を優先する。 |
| UI差異 | FAQまたは画像計画 | 短い案内で済む場合はFAQ、画像が必要な場合は再撮影候補として記録する。 |
| 誤操作 | Commit前チェックリストまたはトラブル集 | Commit前に防げるものはチェックリスト、発生後の対応が必要なものはトラブル集へ置く。 |

第三者テストが未実施の間は、質問頻度や購入者の反応を推測で追記しない。

## 9. Version 1.0で必要な完成条件

| 付録 | 販売用として十分な状態 |
| --- | --- |
| 用語集 | 初稿必須用語を一文で説明し、本文と矛盾せず、専門用語の循環説明がない。 |
| FAQ | 実体験または第三者テストで確認した質問を中心にし、各回答に安全な確認先がある。 |
| Commit前チェックリスト | 7項目以内で、Current repository、`main`、Changes、Summary、個人情報、Commit目的、Push判断を確認できる。 |
| トラブル集 | 実体験由来の必須項目に、停止理由、確認順、安全な戻り方、やらないことがある。高度な履歴操作を標準解決策にしない。 |

## 10. 作成順序

1. **Commit前チェックリスト**：安全性への効果が最も大きく、本文の正常フローと重複しにくい。
2. **用語集**：本文を止めずに読み進めるための基礎を整える。
3. **トラブル集**：実体験由来の項目だけで初稿を作る。
4. **FAQ**：第三者テスト結果を反映して、実際に必要な項目を確定する。

## 実施前の注意

Version 1.0の付録本文を作成する際も、購入者の質問、販売実績、価格、第三者テスト結果を確認できていない内容は、事実として書かない。外部公開、販売開始、Commit、PushはCEOの承認後に行う。
