## Standard Workflow

<!-- 目的: 小さな依頼でも、確認漏れや不要な変更を防ぎます。入力: 基本はそのまま使えます。注意: 小さな作業では、長すぎる計画を作らず簡潔に進めます。 -->

1. 依頼内容を一文で要約する。
2. 関連ファイルと Git の状態を確認する。
3. このファイルとプロジェクトのルールを確認する。
4. 必要最小限の作業計画を立てる。
5. 依頼に必要なファイルだけを作成・変更する。
6. テスト、内容確認、または整合性確認を行う。
7. 差分を確認する。
8. 実施内容と未確認事項を報告する。
9. 次に行うことを1つだけ提案する。

## Editing Rules

<!-- 目的: 既存の資産や作業途中の変更を安全に守ります。入力: 必要に応じて追加します。注意: 関係のない問題を見つけても、依頼範囲外なら勝手に修正しません。 -->

- 変更前に対象ファイルを読む。
- 依頼に不要なファイルは変更しない。
- 関係のない整形や書き換えをしない。
- 削除・移動・大きな変更の前には、内容と影響を報告する。
- 小さな不足は合理的な仮定を明記して進める。
- 重要な不明点だけを人間へ確認する。
- 既存内容を変更した場合は、理由を報告する。
- 依頼外の不具合は勝手に直さず、必要なら提案だけ行う。

## Content Rules

<!-- 目的: 初心者にも誤解が少なく、公開前に見直せるコンテンツにします。入力: 読者と文体を決めます。注意: 推測・見込み・引用は事実のように扱いません。 -->

- **基本言語:** [例: 日本語]
- **想定読者:** [例: AIツールを初めて使う個人]
- **文体・トーン:** [例: やさしく、具体例を添えて説明する]
- 不明な情報は推測で断定せず、不明・要確認と明記する。
- 推定や仮説には、その旨を表示する。
- 誇張表現や収益の保証をしない。
- 著作権と出典を確認し、必要な引用元を記録する。
- 公開前は人間が最終確認する。

## Coding Rules

<!-- 目的: 小さく安全で、あとから見直しやすい実装にします。入力: 対象OS・環境を記入します。注意: コーディングをしないプロジェクトでは、この節を削除できます。 -->

- **対象OS・実行環境:** [例: Windows 11 / Node.js 22]
- 読みやすさを優先し、必要最小限の実装にする。
- 不要な依存関係を追加しない。
- 想定できるエラーを適切に扱う。
- 実行方法・確認方法を記録する。
- テストしやすい構造にする。
- 秘密情報をコードへ直接書かない。
- `.env` などの秘密情報ファイルを Git にコミットしない。
- テストを実行できない場合は、その理由を報告する。

## Health-Aware Operation

<!-- 目的: 無理なく継続できる進め方にします。入力: 基本はそのまま利用できます。注意: これは一般的な作業支援であり、診断や医療情報の記録は扱いません。 -->

- 一度に大量の選択肢を出さず、推奨案は1つにする。
- 作業は15分・30分・60分程度の小さな単位へ分ける。
- 1日に必ず行うことは1つまでにする。
- 中断時に再開しやすいメモを残す。
- 緊急のことと後回しでよいことを分ける。
- 未完了を失敗として扱わない。
- 依頼外へ作業範囲を広げない。
- 次の一手は1つだけ示す。

## Stop Conditions

<!-- 目的: 危険・不確実・専門判断が必要な場面で、安全に止まる基準です。入力: プロジェクト固有の停止条件を追加できます。注意: 停止時は「問題・影響・推奨する対応」を報告します。 -->

次の場合は作業を止め、人間へ報告する。

- データ消失の恐れがある。
- 秘密情報または個人情報の漏えいが疑われる。
- 指示や方針に重大な矛盾がある。
- 課金・契約・外部公開・外部送信が必要になる。
- 本番環境へ影響する可能性がある。
- 法務・税務・医療・社会保障など、専門家の判断が必要である。
- 当初の依頼から大きく範囲が広がる。
