# トラブル集

この付録は、スターターキットの開発と検証で実際に確認された問題を、初心者が安全に止まるための案内としてまとめた初稿です。通常の進め方は本文の Chapter 00〜11 を優先してください。

個人情報や認証情報が表示されそうな場合、対象リポジトリに自信がない場合、Commit や Push の対象に迷う場合は、その場で操作を止めます。

## 使い方

1. 症状に近い項目を探します。
2. 「まず確認すること」だけを確認します。
3. 自信が戻らない場合は、Commit や Push をせずに人間の承認を待ちます。

## 実体験から作成したトラブル

## Trouble 1：README.md を作ったら Changes に4ファイル表示された

### 症状

README.md を作成したあと、Changes に README.md だけでなく、AGENTS.md、00_Command_Center/ROADMAP.md、00_Command_Center/COMPANY_RULE.md も表示されました。

### なぜ止まるべきか

README.md だけを第2Commitにする予定でも、基盤3文書が未Commitなら、4ファイルが同じ変更として表示されます。対象を確認しないままCommitすると、変更の単位が分かりにくくなります。

### まず確認すること

- 基盤3文書が第1CommitとしてCommit・Push済みか確認します。
- Changes に表示されているファイル名を一つずつ確認します。

### 安全な戻り方

README.md をCommitする前に止めます。初回の教材どおりに進める場合は、基盤3文書を人間が確認して第1Commit・Pushし、Changes が空になってから README.md の作成へ進みます。

### やらないこと

Changes の意味が分からないまま4ファイルをまとめてCommitしません。ファイルを削除して表示を減らそうともしません。

## Trouble 2：作成した空フォルダが GitHub に表示されない

### 症状

パソコン上には作成したフォルダがありますが、GitHub のブラウザ版には表示されません。

### なぜ止まるべきか

作成失敗と誤解して不要なファイルを追加すると、教材で想定していない変更が増えることがあります。

### まず確認すること

- フォルダがローカルには存在するか確認します。
- フォルダ内にGitが追跡するファイルがあるか確認します。

### 安全な戻り方

Git は通常、空のフォルダだけを追跡しません。フォルダ内に作業ファイルが作られた時点で追跡対象になります。初期構成では、空フォルダをGitHubに表示するためだけに操作を増やす必要はありません。

### やらないこと

空フォルダを表示する目的だけで、必要性を確認せず .gitkeep を増やしません。

## Trouble 3：.gitkeep を追加すべきか迷った

### 症状

空フォルダをGitHubに表示するため、.gitkeep を入れるべきか迷います。

### なぜ止まるべきか

.gitkeep はGitの正式な機能ではなく、空フォルダを追跡したいときに使われる慣例的なファイル名です。必要性がない段階で追加すると、確認する変更が増えます。

### まず確認すること

- そのフォルダを空の状態でもGitHubに表示する必要があるか確認します。
- .gitkeep を追加する理由を、今回のCommit目的として説明できるか確認します。

### 安全な戻り方

初心者向けの初期構成では、.gitkeep は必須にしません。必要になった場合だけ、人間が変更内容を確認してからCommitします。

### やらないこと

.gitkeep がないことを作成失敗と扱いません。目的が不明なまま複数の空フォルダへ追加しません。

## Trouble 4：別のローカルリポジトリを開いていた

### 症状

GitHub Desktop で表示しているリポジトリと、作業対象としているリポジトリが一致していませんでした。

### なぜ止まるべきか

別のリポジトリでChangesを確認、Commit、Pushすると、関係のないファイルを変更するおそれがあります。

### まず確認すること

- GitHub Desktop の Current repository を確認します。
- リポジトリ名、ローカルパス、branch が対象と一致するか確認します。
- 本番リポジトリではなく、テスト用Privateリポジトリか確認します。

### 安全な戻り方

正しいリポジトリを開くまで、ファイル作成、Commit、Pushを進めません。確認できたら、そのリポジトリのChangesをあらためて確認します。

### やらないこと

見慣れた名前に見えるという理由だけで操作を続けません。対象が不明なままCommitやPushをしません。

## Trouble 5：Codex と GitHub Desktop の認識が一致しない

### 症状

Codex のGit確認と、GitHub Desktop またはブラウザ版GitHubで見えるChangesや反映状態に差がありました。

### なぜ止まるべきか

どの状態を基準にすべきか曖昧なまま進めると、想定外のファイルをCommitしたり、別リポジトリを確認したりする可能性があります。

### まず確認すること

- GitHub Desktop、ローカルGit、ブラウザ版GitHubを別々の確認先として扱います。
- それぞれでリポジトリ名、branch、ChangesまたはCommit履歴を確認します。
- 直前にCommitやPushをしたかを確認します。

### 安全な戻り方

差が解消するまで次のCommitやPushを進めません。人間がGitHub Desktopで表示内容を確認し、必要に応じてブラウザ版GitHubで反映を確認してから再開します。

### やらないこと

一つの画面だけを見て、他の状態を確認せずに結論を出しません。表示差を埋めるために履歴を書き換えません。

## Trouble 6：Commitメッセージが重複して見えた

### 症状

検証用のCommit履歴や撮影画像で、基盤3文書のCommitメッセージに文字列の重複が見つかりました。

### なぜ止まるべきか

正常フローの見本と実際の失敗例を混同すると、初心者が同じ入力を正しいものだと受け取る可能性があります。

### まず確認すること

- Summary欄の入力が一度だけで、今回のCommit目的と一致しているか確認します。
- Changesに含めるファイルがSummaryの内容と一致しているか確認します。
- すでにPush済みか確認します。

### 安全な戻り方

Commit前なら、SummaryとChangesを人間が確認してからCommitします。Push後に気付いた場合は、急いで履歴を変更せず、ファイル内容とCommit履歴を確認して状況を記録します。個人情報や認証情報が含まれない場合は、必要な修正を次のCommitで行えることがありますが、方針は人間が確認して決めます。

### やらないこと

Commitメッセージを画像上で書き換えて正常例に見せません。force push、reset --hard、公開済み履歴の書き換えを標準の解決策にしません。

## Trouble 7：Push後にCommitメッセージのミスに気付いた

### 症状

Pushしたあとに、Commitメッセージが意図どおりではないことに気付きました。

### なぜ止まるべきか

Push後は他の人が履歴を見る可能性があります。慌てて履歴を変更すると、問題の範囲を広げることがあります。

### まず確認すること

- GitHub上でCommit履歴とファイル内容を確認します。
- 間違いがCommitメッセージだけか、ファイル内容にもあるか確認します。
- 個人情報や認証情報が含まれていないか確認します。

### 安全な戻り方

追加のCommitやPushを急がず、人間が状況を確認します。ファイル内容に問題がなく、個人情報や認証情報が含まれていない場合は、次のCommitで必要な説明や修正を行えることがあります。

### やらないこと

公開済み履歴をすぐに書き換えません。force push や reset --hard を初心者向けの通常手順として使いません。

## 検証待ちの候補

次は第三者テストではまだ確認されていないため、現時点では標準のトラブル手順にしません。

- Push origin が表示されない場合の案内
- 教材とGitHub DesktopまたはGitHubのUIが大きく異なる場合の案内
- テスターが途中で再開位置を見失う場合の案内

第三者テストで実際の症状、操作、質問が確認できたら、実体験由来の項目と区別して追加を判断します。

## 共通してやらないこと

- 対象リポジトリやCommit対象に自信がないままCommit・Pushしない
- 個人情報や認証情報をCommit、Push、画面共有、記録に含めない
- force push、reset --hard、公開済み履歴の書き換えを初心者向けの標準対応にしない
- 問題を隠すためだけのCommitを作らない
